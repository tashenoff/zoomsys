# Задача для Гермеса: Zoomsys — код, прайсы и сиды

Разверни подготовленные изменения Zoomsys из `origin/codex/canvas-operations` и примени сиды текущего обновления. Используй точный SHA, переданный пользователю после пуша. Не трогай MedCRM, CallIQ, клиентов и заказы. Сохрани изменённые менеджерами цены и ID существующих позиций.

## 1. Определи фактическое окружение

Найди действующий checkout и способ запуска Zoomsys на VPS по текущей конфигурации. Не угадывай каталог, IP, базу или compose project. Проверь `git remote -v`, текущий commit, `git status --short`, работающие контейнеры/сервисы и целевую БД без вывода паролей и токенов. Если checkout содержит чужие изменения, не делай reset/clean: остановись и сообщи, что мешает обновлению.

В репозитории предусмотрены compose-сервисы `app` и `postgres`, контейнеры `zoomsys-app`/`zoomsys-db`. Примеры ниже применять только после проверки, что это действующий стек Zoomsys. Для иной схемы запуска адаптировать команды к найденному окружению и показать её в отчёте.

Фронтенд и API разделены: Dockerfile собирает **только API**, UI размещается отдельно. Проверь фактический production-проект фронтенда и его ветку/пайплайн. Один запуск сидов не обновит кнопки и интерфейс калькуляторов. Не создавай новый Vercel-проект и не меняй API URL наугад.

## 2. Сначала резервная копия базы

Из каталога проверенного compose-проекта, в bash:

```bash
set -euo pipefail
umask 077
backup_dir="$HOME/zoomsys-backups"
mkdir -p "$backup_dir"
backup_file="$backup_dir/zoomsys-before-pricing-$(date -u +%Y%m%dT%H%M%SZ).dump"
docker compose exec -T postgres sh -lc 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > "$backup_file"
test -s "$backup_file"
docker compose exec -T postgres pg_restore --list < "$backup_file" > /dev/null
printf 'Backup verified: %s\n' "$backup_file"
```

При ошибке бэкапа не продолжать. Зафиксировать текущий SHA и ID образа API для возможности возврата. Снять агрегированные контрольные показатели клиентов/заказов/позиций заказа (количество и максимальный ID), не выводя личные данные.

## 3. Получи и проверь код

```bash
git fetch origin
git log -1 --format='%H %s' origin/codex/canvas-operations
git status --short
```

Сверь SHA с сообщением пользователя. Обнови release checkout через существующий процесс, без force/reset/clean. `git merge --ff-only origin/codex/canvas-operations` допустим только если текущая ветка является предком нужного коммита и рабочая копия чистая. При расхождении веток сообщи об этом; не переписывай историю.

## 4. Собери API и примени обновление

Для подтверждённого compose-стека:

```bash
docker compose build app

# План читает только pricing.json; подключения к БД нет.
docker compose run --rm --no-deps app node seed-updates-2026.js --plan

# Схема и адресные миграции; затем только набор текущего обновления.
docker compose run --rm --no-deps app node migrate.js
docker compose run --rm --no-deps app node seed-updates-2026.js

# Повторный запуск должен дать inserted: 0.
docker compose run --rm --no-deps app node seed-updates-2026.js

docker compose up -d --no-deps app
curl --fail --silent --show-error http://127.0.0.1:3001/api/health
```

План содержит 204 кандидата: 37 карточек, 23 материала широкоформатной печати, 9 текстильных материалов, 18 готовых флаговых позиций, 3 стенда, 3 способа нанесения, 68 позиций госсимволики и 43 операции. Это проверяемые исходные записи, а не ожидаемое число новых строк.

Сид выполняется транзакционно: добавляет отсутствующие записи, сохраняет ID, отключённые позиции и изменённые цены. Известные старые тарифы/ширины меняются только при точном совпадении с `price-corrections-2026.json`. `priceCorrections.unchanged` включает уже исправленные, отсутствующие и изменённые менеджером записи — проверь их, не перезаписывай принудительно. Полный `seed.js` для существующей БД не нужен.

Если API работает без Docker, используй его действующее окружение и DATABASE_URL, не копируй секреты в команды/чат. Эквивалент из release checkout: `npm --prefix server run migrate`, затем `npm --prefix server run seed:updates-2026`. Перезапускать только найденный сервис Zoomsys.

## 5. Обнови фронтенд штатным пайплайном

Опубликуй тот же проверенный commit в существующий production-проект UI по действующей схеме. Если для этого требуется merge в другую ветку, а полномочия/целевой проект неясны — сначала верни точный блокер. Проверь успешную сборку и фактическую версию UI; не считай обновление базы доказательством обновления фронтенда.

## 6. Проверь результат

Через действующий авторизованный API/прайс и интерфейс:

- №33: рекламные стенды не предлагают «Натяжку холста» и «Подрамник»; кармашки и кайма остались.
- №34: обе операции есть только у холста Mimaki/Roland. У винила/баннера их нет. Существующие тарифы и ID сохранены. В локальном исходном прайсе натяжка 3500 ₸/м², подрамник 3000 ₸/пог.м. Общий объём вводится на весь заказ: 1 м² + 4 пог.м добавляют 15 500 ₸ к печати, если менеджер не менял эти тарифы.
- Ведомственные таблички переименованы адресно; цены и старые заказы не изменены.
- В прайсе сублимации есть варианты «Кружка белая»/«Кружка перламутровая», они доступны в калькуляторе и сохраняются в заказе. Новые ставки за заготовку не добавлялись.
- Для нестандартного флага размеры задаются в метрах; расчёт идёт по текстилю и выбранным обработкам. Пример исходного прайса: атлас 1,2×1,7 м, 2 шт., прошивка, без срочности: печать 30 600 + прошивка 8700 = 39 300 ₸. Прошивка — отдельная строка, 11,6 пог.м. Свыше 500 пог.м выводится договорная цена.
- Roland: ширина винила 1,2 м. Для 45 наклеек 0,15×0,30 м, зазора 0, припуска 0,2 м: 3×15 с поворотом, площадь печати 2,695 м². По исходным тарифам 4 проходов печать 12 127,50 ₸; отдельно введённая резка 2,025 м² — 4050 ₸; итог 16 177,50 ₸.
- Визитки/дисконтные карты: видимая кнопка «Рассчитать», корректные тарифы по тиражу. Бейджи: кнопка есть, выбор цветности не обязателен, требуется согласованная сумма за тираж; автоматической ставки 7 ₸ нет.
- Выбор клиента, сохранение и повторное открытие тестового заказа сохраняют размеры, выбранные варианты и операции. Тестовые записи в production создавать только в согласованном тестовом клиенте/порядке; существующие записи не редактировать для проверки.

Сверь контрольные показатели заказов/клиентов с учётом поступивших во время работ новых заказов. Сиды не должны менять старые позиции заказов.

## 7. Отчёт и ошибка

Верни: SHA кода API/UI, фактический сервис/базу без секретов, путь проверенного бэкапа, результаты migrate и двух запусков сида, health check и UI-проверок. Не заявляй успех по одному только exit code сборки.

При ошибке останови зависимые действия и сообщи точную команду, причину и уже выполненные изменения. Сид откатывает свою транзакцию; общая миграция — отдельный этап. Не удаляй Docker volumes и не запускай pg_restore поверх production автоматически: восстановление может затереть новые заказы и требует отдельного согласования. Не применяй посторонние сиды, не используй `git push --force`.
